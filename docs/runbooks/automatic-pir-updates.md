# Coordinator-authorized automatic PIR updates

Automatic updates are optional. The host follows the `binary_tag` and
`snapshot_height` selected in its configured `pir.json`, only when an adjacent
`pir_attestations.json` verifies under the compiled **valargroup** coordinator
public key for the configured environment. Production and staging pin separate
valargroup keys; signatures are also scoped so they cannot be reused between
environments.

## Maintainer workflow

1. Publish a compatible nf-server release and the intended network-specific
   snapshot. This release must support `build-info`, `verify-pir-update`, and
   `snapshot-stage`. Linux amd64 uses the existing x86-64-v4/AVX-512 release
   requirements; Linux arm64 uses the native ARM release.
2. Open **Authorize PIR update** in the vote-sdk admin dashboard connected to
   the intended environment. Its `SVOTE_ZCASH_NETWORK` must be configured.
3. Select the environment, explicit release tag, and snapshot height. Review
   the proposed pair, network, and artifact hashes. Check that the snapshot is
   appropriate for the active voting round.
4. Connect the valargroup coordinator's Keplr wallet, then **Sign and create
   pull request**. Signing uses the existing local coordinator derivation flow.
   Use the valargroup key pinned for the selected environment. If its derivation
   chain differs from the connected chain, set **Signing key’s original chain ID**
   to the chain where that key was derived and connect that chain in Keplr first.
5. Review and merge the PR in token-holder-voting-config. The PR commits both
   files together. Publication validates signatures; enrolled hosts validate
   them again independently before changing anything.
6. Inspect each host's `/metadata` and updater status for convergence. A valid
   signed rollback selects an older tag/height through the same workflow.

`pir.json` gains only `binary_tag`:

```json
{
  "schema_version": 1,
  "snapshot_height": 3484440,
  "binary_tag": "v1.2.3"
}
```

The tag above is illustrative. Do not select a release until its compatible
artifacts and snapshot are published. Existing snapshot-only configuration
continues to publish until the coordinator creates the first signed update.
No signatures or initial live release selections are generated by installing
this implementation.

## Enrollment

An existing `start_pir.sh` installation can enroll directly, including older
servers without `build-info` or `/metadata`. The service must be ready, its
running executable must match the installed file, and its local snapshot must
match the configured network. A manual application upgrade is not required.

The versioned installer downloads and checksum-verifies its own release's
`nf-server` as a separate `/opt/pir-updater/verifier`. That pinned verifier
validates the signed config; the application version is selected by `binary_tag`
and can differ from the installer release. The existing process keeps serving
while authenticated artifacts are staged. The installer then activates the
signed target, waits for exact readiness, and leaves future polling enabled.
It exits nonzero on failure and restores the original service if activation began.

Download the trusted installer from the released assets or Spaces, inspect it,
and run as root:

```bash
curl -fsSLo install_pir_updater.sh \
  https://shielded-vote.nyc3.digitaloceanspaces.com/install_pir_updater.sh
sudo bash install_pir_updater.sh
```

Version-specific installer URL:
`/scripts/install_pir_updater/<tag>/install_pir_updater.sh` on the same Spaces
origin. New installations can pass `--auto-update` to `start_pir.sh`.

The initial installer and release are the trust bootstrap; downloading a key
next to the config is not a substitute for trusting the initial installation.
No GitHub, Spaces, or coordinator private credentials are installed on hosts.
The installer requires Linux/systemd, Python 3, curl, CA certificates, and
`flock` (util-linux). It preserves the base environment files and rejects
forced snapshot settings, custom ExecStart commands, and existing systemd
overrides that need an operator migration.

If enrollment is interrupted before activation, the original service remains
unchanged. Once activation begins, the installed timer also handles recovery
after a crash or reboot. Recovery restores the original executable, unit, and
data path, with a systemd override that disables remote snapshot discovery.
The override is installed before activation and retained after recovery so a
reboot cannot replace the rollback snapshot or require a working config endpoint.
Enrollment checks the legacy server's `serve --help` for `--pir-data-dir` and
`--voting-config-url`; `--pir-config-url` is disabled only when supported.
A legacy server is checked using its executable hash and `/ready`, without
requiring `/metadata`. Rerun the installer to retry a restored migration;
it accepts its own exact recovery override. To return to manual snapshot
discovery instead, review and remove
`/etc/systemd/system/nullifier-query-server.service.d/90-pir-updater.conf`
and run `systemctl daemon-reload` before restarting the service.

A repeated invocation of this installer on an enrolled host immediately
reconciles the signed target and enables polling after success. It reuses the
installed updater and verifier; it does not implicitly rotate keys or replace
updater code. Hosts enrolled with older installers retain their older rerun
behavior and need an explicit operator-managed updater migration.

## Operation and recovery

```bash
sudo python3 /opt/pir-updater/pir_updater.py status
sudo python3 /opt/pir-updater/pir_updater.py retry-now
systemctl status pir-updater.timer pir-updater.service
journalctl -u pir-updater.service -u nullifier-query-server.service
curl -fsS http://127.0.0.1:3000/metadata
```

The timer polls every 60 seconds with up to 30 seconds of jitter; gateway caches
may add delay. Downloads can take substantially longer. Verified artifacts are
staged while the current process serves. Activation restarts the server and
waits up to 600 seconds (configurable at enrollment with `--timeout-secs`).
Readiness must match the exact running tag, network, and loaded snapshot height.

A failed activation restores the previous binary, data path, and service unit.
An interrupted transaction is rolled back on the next updater invocation.
Retries back off from one minute to one hour. Failed rollback retains the
journal and reports an error for subsequent recovery. Generation files are
retained until successful activation allows cleanup; allow space for active,
previous, and incoming snapshots plus server precompute caches.

Status is also available at `/var/lib/pir-updater/status.json`. `/metadata`
exposes running identity and update state. Existing private `/metrics` includes
`nf_build_info`, `nf_updater_desired_info`, desired height, convergence,
verification/update timestamps, failures, and rollbacks. No new Sentry events
are emitted by the updater.

To pause:

```bash
sudo python3 /opt/pir-updater/pir_updater.py disable
sudo systemctl enable --now pir-updater.timer  # resume
```

To remove scheduling and detach the managed executable:

```bash
sudo python3 /opt/pir-updater/pir_updater.py uninstall
```

Uninstall leaves the current process and retained snapshot running. It preserves
an explicit data-path systemd override and retained files so a subsequent
restart stays on that snapshot. Review/migrate that override before re-enrolling.
The manual updater, `start_pir.sh` reruns, GitHub deploy action, and restart
workflow refuse enrolled hosts, including interrupted enrollment. Use coordinator
updates or uninstall first. Disabling the timer alone does not opt out of this
protection. These entrypoints hold `/run/lock/pir-update.lock` across the ownership
check and serving-path changes. GitHub deployment uploads to a run-specific
temporary directory, then checks ownership again under the lock before installing;
it keeps the lock through readiness and forced-snapshot cleanup.

## Signed format and trust boundaries

`pir_attestations.json` contains `schema_version: 1`, `payload`, and `signatures`.
Each signature contains `key_id`, `alg: "ed25519"`, and a base64 64-byte `sig`.
The payload has exactly five lowercase SHA-256 strings, in this signing order:

1. `config_sha256`: exact bytes of `pir.json`, including whitespace/newlines.
2. `linux_amd64_sha256`.
3. `linux_arm64_sha256`.
4. `snapshot_manifest_sha256`: exact manifest bytes; the manifest authenticates
   the snapshot file contents and sizes.
5. `service_sha256`: `nullifier-query-server.service`.

The monitoring sidecar is outside this trust boundary. `pir-apm` is not on the
serving path, is not signed by the coordinator, and is updated by a separate
service that shares no state or lock with this one. See
`docs/runbooks/pir-apm-updates.md`.

The Ed25519 message is UTF-8 `valargroup/pir-update/v1\n`, then `prod\n` or
`stage\n` from the installed config scope, then each of those five lowercase
hex strings followed by `\n`. These are actual LF bytes, not backslash-n text.
The test vector in `testdata/pir-update-vector.json` is shared with Go, TypeScript,
and publication verification. It uses a test-only key that production verifiers
never trust.

The installed verifier checks authorization before any downloaded executable
runs. The candidate validates its snapshot only after binary hash verification.
The updater does not refresh its own code or trusted keys automatically; key
rotation requires an explicit operator-managed verifier update.

There is intentionally no revision or expiry. Old authentic configurations can
be replayed, and an attacker can withhold newer updates. Invalid/missing or
mismatched documents leave the running generation unchanged. A compromised
valargroup signing key can authorize software installation; optional enrollment
means choosing to trust that authority. Independent polling provides no fleet
availability guarantee: hosts can restart at overlapping times.

## Tests

```bash
cargo test -p nf-server --features serve
python3 -m unittest discover -s deploy/pir-updater -p 'test_*.py'
scripts/test_pir_updater_systemd.sh
```

The systemd test runs in a disposable privileged Docker container with a native
executable HTTP fixture, exercising legacy bootstrap, installed/running identity
mismatch, rejection before activation, failed activation rollback without
metadata, interrupted enrollment recovery, and installer reruns without touching
live infrastructure. Legacy recovery is tested with changed and unavailable remote
configuration and with a binary lacking `--pir-config-url`. Manual-entrypoint tests
exercise enrollment rejection, lock contention, and enrollment between deployment
preflight and installation. Unit tests cover signature-before-execution, file mismatches,
backoff, interrupted transactions, fallback downloads, and target changes.
